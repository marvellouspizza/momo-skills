# 三次人工审核的游戏制作工作流

# Context
我从小就喜欢玩《敲砖块》, - 里面各种剧情 玩法 装备 PK 机制等都很吸引我 

# Goal
我现在如果要复刻一个这样的游戏（重置成 web 应用）  (请你将产生的所有文件放到这个目录下 `/Users/momo/Documents/Games-AI/敲冰块`)
1. 做出首个可玩样板，保证我可以最简单地开始
2. 需要准备媒体、美术资源的 请你列一个资产清单 准备资产后 再进行后续的开发 美术生产标准：统一像素尺寸、角色比例、动画锚点、图集与资源映射。
3. 出具完善清单
4. 商业版验收：全剧情可通关、正式资产齐全、存档恢复与迁移、移动端兼容、性能测试、部署回滚及源码交接。
5. 我的目标是超越这个作品 成为一个所有人都能玩的经典
6. 整体保持商业交付级别的架构、审美和品味, 交互要保持现代化 国际化 高审美 简洁 生动活泼

（如有必要 可以使用动态工作流, 子 Agent 分任务执行并逐项复核）


===

## 用途与开源资源

游戏仅用于非商业用途，按商业交付级别的质量标准制作。优先复用许可允许且适合游戏的开源音效，缺失或不适配时再生成；可参考开源地图及其他资源，使用时记录来源并遵守许可与署名要求。

## 执行边界

你负责从设计、资源生产到实现、验证和交付。完成标准是获批范围全部兑现；不要停在计划、静态页面或样板。

- 常规人工审核只有三次：界面参考图 → 首个可玩样板 → 完善清单。各节点等待明确批准；退回就在当前节点修正，沉默不算批准。第三次批准后连续制作到交付，不再逐项询问是否继续。
- 清单是交付基线。模型自主决定实现方案、任务拆分和执行顺序，主动改善玩法、地图、叙事、音画与交互；保留获批体验与必做结果，不擅自缩减承诺或扩大项目。
- 参考清单只借鉴适用的分析方法，不继承其他游戏的系统、数量、工期、技术栈或完成状态。文档形式按项目规模选择，记录能支撑实现、审核与恢复的信息即可。
- 普通技术问题自行解决；真实缺失的必要输入、指定模型不可用或超出现有外部操作授权时才报告阻塞，同时推进独立工作。未授权发布时交付可部署产物；不把最终交付变成第四次人工审核。

## 1. 建立基线，提交参考图〔人工审核 ①〕

读取项目指令、现有实现、资源与历史批准记录。确定当前游戏、工作目录、核心循环、目标平台和输入方式、交付范围；继续已有项目时保留有效成果和批准节点。缺省采用可直接游玩的 Web 方案，并支持桌面与触屏。

分析原作值得保留的体验与可改善之处，为本作选择有辨识度的提升方向，写明预期玩家收益和验证方式；不要靠增加功能数量代替“超越”。参考不足时区分已知事实与设计假设，不能编造原作表现。

生成能表达实际玩法的主界面参考图，按需要补充关键界面或移动布局。明确构图、视角、配色、角色比例、UI 层级和动效方向，给后续资源与代码提供共同基准。先经 Astra 独立审核并修正，再向用户一次提交图片、玩法方向与关键假设。批准后锁定方向，细节可持续优化。

## 2. 准备资产，交付可玩样板〔人工审核 ②〕

建立资产清单，记录用途、规格、来源或提示词、文件路径及“待生产／待审核／可接入／已接入”状态。按样板所需最小集合先生产和审核资源，再开发依赖这些资源的功能；无资产依赖的工程准备可并行。

- 按美术类型统一尺寸、角色比例、动画锚点、朝向、帧序、图集和资源映射；检查地图块接缝、遮挡、碰撞轮廓与实际显示尺寸。静态图不能冒充动画成品。
- 使用内置图像生成能力批量生产，保存提示词、结果与失败状态，支持断点续作。优先采用当前可调用的入口；无头入口须先验证可用，失败时切换可用的内置入口，不因推测额度不足而缩减资源。
- 按需要使用 ElevenLabs 等可用音频工具，检查格式、音量和循环衔接。调用凭据从环境变量读取，不复制进游戏源码、日志或交付包。
- 资产须有可用来源；生成、审核、接入分别核验，文件存在不代表游戏已正确使用。

做出真实可操作的核心循环：玩家行动能改变状态、产生反馈并继续游玩。战斗游戏验证命中、胜负和重试；探索、创造或叙事游戏按自身目标形成闭环，不强加战斗系统。样板应验证手感、节奏和正式视觉方向，提供最简启动入口。

Sol 审核实现与功能，Astra 审核实际画面与样板地图；修复阻断问题后，提交可玩入口、操作说明、运行截图或录屏，以及完整版尚缺的内容。用户批准核心体验后进入完善清单阶段。

## 3. 制定完成范围〔人工审核 ③〕

依据用户目标、获批样板和审核发现制定完善清单。每项说明要解决的问题、交付结果、优先级与验收方法；按需要附依赖、资产及证据位置。区分必做项、自主优化空间和后续建议，防止遗漏与无边界扩张。

参考清单可用于组织现状与缺口、关键依赖、体验指标、里程碑、资源进度和原创提升。只选择当前游戏适用的结构；无需复制页面或凑齐条目。

检查清单是否覆盖承诺的全部玩法与内容、地图连接、正式资产、引导和设置、存档恢复与迁移、平台兼容、性能、部署回滚与源码交接。不适用项说明理由，不能默默省略。性能目标须有设备、场景和测量方法；原创提升须有可观察的玩家收益。

Sol 检查可实现性、依赖和可测试性，Astra 检查美术与地图内容是否完整。修正后一次提交清单、范围取舍和验收条件。用户批准的版本作为完成度分母，内部任务允许继续演进；不得靠删项宣布 100%。

## 4. 自动制作与独立审核

按依赖分批执行：资产就绪 → 实现 → 测试与试玩 → 独立审核 → 修复复核 → 更新完成证据。无依赖任务可委派子 agent 并行，明确文件责任，整合后验证。持续推进到验收完成；进度通知不要求用户确认。

沿用项目架构与约定，分离规则、状态、输入和表现，避免未获批系统的过度设计。对核心规则、状态转换、存档和跨系统交互采用可复现的测试；修复重要 bug 时补充能复现问题的回归检查。纯样式微调用画面验证，避免只复述实现的测试。

### 固定审核模型

| 领域 | 独立子 agent 模型 | 审核时机 |
| --- | --- | --- |
| 代码、架构、功能、玩法逻辑、测试与工程交付 | `gpt-6.1-sol` | 样板、完善清单、每个实质功能批次及核心逻辑/存档/架构改动、最终整合版本 |
| 美术、地图完整性、美观与视觉体验 | `gpt-6-astra` | 参考图、样板、完善清单、资产/地图批次、最终整合版本 |

必须实际启动对应模型，主 agent 自检或实现者自审不能代替独立审核。使用 `collaboration.spawn_agent` 时显式指定 `model` 和 `fork_turns: "none"`；其他调度器用其支持的等效参数，并确认实际模型。模型不可用时恢复调度或记录阻塞，不静默替换。

向审核者提供目标、验收条件、稳定版本、改动范围、运行方式及原始证据。Sol 读取相关代码并核验测试；Astra 查看图片或实际运行画面，地图同时查看全区覆盖、玩家视角与通路证据。两类审核不能相互代替。

报告只需记录模型、版本、覆盖项、结论、未验证项和问题证据。问题按影响分类：P0 为无法运行、数据损坏或进程阻断；P1 为核心功能错误、必要内容缺失或明显视觉问题；其余为 P2。个人风格偏好与可选创意建议不得伪装成缺陷，原创实现不因未照搬参考而判失败。

主 agent 修复后交指定模型复核受影响项，通过后关闭问题。连续修复无进展时先缩小复现、重查根因或更换路线；只有缺少外部条件或必须改变用户承诺时才请求输入。审核后修改了实现，补做受影响范围的复核。

## 5. 成品验收与交付

每个必做结果关联实现、验证证据与审核结论；依赖项或验收未完成时不得标记完成。对照以下维度实际验证，按玩法选取适用场景：

| 验收面 | 通过依据 |
| --- | --- |
| 全流程 | 从新游戏到全部获批关卡/剧情结局；覆盖主要分支、失败恢复和结算。无终点玩法验证完整对局、代表循环或约定持续时长，调试跳关不能代替通关 |
| 地图 | 必要区域、连接、目标和交互均存在且可达；出生、出口、边界、遮挡与重生有效，没有意外软锁 |
| 正式资产 | 清单、文件和运行时引用一致；无缺失或未获批占位资源，动作、锚点、音画与 UI 在游戏内正常 |
| 数据可靠性 | 存档持久化、恢复、版本迁移和损坏数据处理通过；按适用情况验证联网中断与重连 |
| 平台与性能 | 获批平台、输入、布局和关键压力场景通过实测；记录环境及性能结果，模拟器结果不能写成真机结果 |
| 交付工程 | 干净安装、生产构建、产物启动与关键路径测试通过；源码、依赖、资产来源、部署与回滚方法齐全，说明演练环境 |
| 原创提升 | 用同类体验场景对照既定提升目标，提供操作、画面或测量证据；审美判断说明依据，缺少原作证据时不宣称全面超越 |

最终整合版本通过 Sol 与 Astra 审核，获批必做项验证通过率达到 100%、P0/P1 清零、其余问题满足获批标准，才能宣布完成。该比例表示承诺兑现，不表示零 bug；未验证项和残留问题如实列出，不能用构建成功或漂亮截图代替成品验收。

持续保存当前阶段、三次批准依据、获批范围、资产与任务状态、审核证据、运行入口和下一步；复用现有项目记录，避免重复文档。中断或上下文压缩后先恢复状态，不重做已有效批准的关卡。

交付可玩入口或产物、最简运行说明、源码与正式资源、完成清单与审核证据、平台性能结果和部署回滚说明。真实阻塞则交付已完成部分与可恢复状态，明确缺失条件；不把部分完成写成成品。
